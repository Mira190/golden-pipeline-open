# Red-team review, 2026-10-22

**Scope:** the gate logic (`src/golden`), the reusable workflows, and the work of the parallel
"CI checks and workflow optimisation" session (branch `claude/exciting-newton-q0imwh`, merged
into `claude/zealous-lamport-35rr0y`).

**Question:** given the goal of a Golden Pipeline that relies on the system rather than on
people for QA, where can a change still get through without being checked, and where does the
system block good work so that people learn to route around it?

**Method:**

- Read the code and workflows from first principles: who controls each input to a gate?
- Encode every finding that the CLI can observe as a labelled scenario in
  [`evals/`](../../evals/README.md), so a fix is proven and the finding can't silently come back.
- Findings that need GitHub itself (rulesets, labels, check runs) are listed here with a concrete
  fix.

Severity is *what an author could get merged without a check*: **High** means an untested or
unreviewed change reaches the default branch with a green check.

## Open findings and recommendations

### R1 — A pull request runs its own copy of the caller workflow (High)

On `pull_request` events GitHub runs the workflow file *from the pull request*. A PR that edits
`.github/workflows/ci.yml` can do either of these and still get a green `ci / golden`:

- set `test-command: cp tests/fixtures/full.xml coverage.xml` (fake coverage)
- set `mutation-command: echo '{"killed": 1}' > mutants/mutmut-cicd-stats.json`

**Status:**

- `docs/security-model.md` now says this (CI session).
- Scorecard L3 `owner-review` verifies the mitigation is configured.
- Repositories at L2 remain exposed.

**Recommendations:**

1. **Organisation ruleset → "Require workflows to pass before merging"** for every repository
   that adopts the pipeline. It runs the workflow from the central repository, so a PR cannot
   edit its judge. This is the real fix for centralised governance. Add it to
   `docs/adoption.md` as step 1 for organisations.
2. *(done, F11)* In the `plan` job, flag a PR that changes the workflow judging it:
   `git diff --quiet "$BASE"...HEAD -- .github/workflows/` → a `::warning::` and a
   job-summary banner, "This PR changes the workflow that gates it; a code owner must
   review". This is visible to every reviewer and costs nothing.
3. Consider making `scorecard.min_level = 3` the default for repositories that deploy to
   production (a policy decision; see `docs/evaluation.md`).

### R2 — The opt-out label is self-service (High)

Anyone with triage rights can apply `no-tests-needed`, including the PR author. The CI session
made the label take effect immediately (`labeled`/`unlabeled` triggers). That is correct, but it
also makes the bypass instant.

**Recommendation** *(plan job)*: read the PR's label events (`GET
/repos/{repo}/issues/{n}/events`, `pull-requests: read`) and honour the label only when someone
other than the PR author applied it. At minimum, write who applied it into the job summary.

### R3 — The coverage report is produced by the code under test (Medium)

`coverage.xml` is written by the test job, which runs the PR's code. A `conftest.py` that
rewrites the report at session end games diff coverage and the ratchet.

**Mitigations:**

- Mutation testing re-runs the tests under its own control and remains the backstop.
- Reviewers see the conftest change.

**Recommendation:** add a drill scenario, "conftest rewrites coverage.xml", to
`scripts/drill.py`. It should prove that the mutation gate still blocks.

### R7 — A source change that makes an *existing* test flaky is not re-run (Low)

The flake gate re-runs changed tests only. A race introduced in source code shows up later, as
an "unrelated" red on someone else's PR. A DeFlaker-style classification (a failing test that
covers no changed line is probably flaky) would turn those into actionable reports. That is a
candidate for a later version (see research §12).

### R8 — Ruleset bypass actors are invisible to the scorecard (Low)

`required-check` passes when the rule exists. An admin bypass list still lets people merge
red. The branch-rules API doesn't expose bypass actors.

**Recommendation:** in the scorecard, read `GET /repos/{repo}/rulesets/{id}` when the token
allows it and report bypass actors. Otherwise show "unknown", and unknown never counts as a pass.

## Process note for parallel sessions

Two sessions hardened the same modules concurrently, which produced a 12-file merge. Some fixes
were written twice, sometimes with different messages and semantics: runnable Node tests, path
normalisation, policy validation. Two things helped:

- **The decision benchmark acted as a shared contract.** After the merge, the strict xfail on
  `presence/python-unicode-filename` failed. The other session's `gitdiff` fix had closed a
  known gap, and the suite forced the label off.
- Conflicts were resolved by keeping both behaviours wherever they did not contradict, and by
  adopting the safer rule where they did. For example, Node helpers under `__tests__/` are not
  runnable.

For the next round:

- **Claim modules up front.** Gate logic and evals in one session; workflows, examples and
  release in the other.
- **Every fix lands with a scenario** in `evals/scenarios/`. Then a merge that undoes someone
  else's fix fails the suite instead of passing review.
